## API revision — 2026-08-02 (second pass: readability)

A source-review pass (the user reading the actual `.go` files, not just using the API) flagged two constructs as harder to follow than they needed to be: the reverse `for` loop in `Chain` that reassigns its own parameter, and the functional-options mechanism (`type Option func(*App)` plus a dozen `WithX` functions) used to configure `App`. Resolved the same day, the second one via one clarifying round on how far to go and one more on `New`'s exact signature (both recorded here so the reasoning isn't lost):

27. ✅ **`Chain`'s loop no longer reassigns its parameter.** `middleware.go`'s `Chain` used `for i := len(mw)-1; i >= 0; i-- { h = mw[i](h) }`, reassigning the `h http.Handler` parameter in place — correct, but easy to misread as mutating the caller's handler rather than building a new one. Rewritten to accumulate into a separate `wrapped` variable (parameter renamed `final`), with a comment explaining the reverse iteration. Behavior is byte-for-byte identical; this is a readability-only change.
    Done when: `go test ./...` passes unchanged (no test needed updating — same inputs, same outputs), confirming the rewrite didn't alter `Chain`'s semantics.

28. ✅ **Functional options (`Option`, `WithAddr`, `WithEnv`, `WithLogger`, `WithConfig`, `WithReadTimeout`, `WithReadHeaderTimeout`, `WithWriteTimeout`, `WithIdleTimeout`, `WithShutdownTimeout`, `WithOnStart`, `WithOnShutdown`, `WithBaseContext`) replaced by a single exported `AppConfig` struct.** `New(opts ...Option) *App` is now `New(cfg ...AppConfig) *App` — `cfg` is variadic *only* to keep `gwt.New()` (no argument) working for the zero-config case; passing more than one `AppConfig` is meaningless and only `cfg[0]` is used. `AppConfig` has five fields: `Config Config`, `Logger *slog.Logger`, `OnStart []func(context.Context) error`, `OnShutdown []func(context.Context) error`, `BaseContext func(net.Listener) context.Context`. The five granular timeout options collapsed into just setting fields on `AppConfig.Config` directly — no separate `WithReadTimeout` etc. A new unexported `resolveConfig(c Config) Config` in `config.go` fills any zero-value field of `AppConfig.Config` from `defaultConfig()`, so `AppConfig{Config: Config{Addr: ":9000"}}` still gets safe non-zero timeouts everywhere else (the trade-off: there's no longer a way to explicitly force a zero timeout — a zero value always reads as "unset, use the default"). Every call site across the library, its tests, `examples/basic`, and `cmd/gwt-cli/templates/main.go.in` was converted from `WithX(...)` chains to `AppConfig{...}` struct literals.
    Done when: `go build ./...`, `go vet ./...`, `go test ./...`, and `go test -race ./...` are clean with zero references to `Option` or any `WithX` function remaining anywhere in the module (library, tests, scaffolder templates, docs). `TestAppConfigPartialConfigFillsMissingFieldsWithDefaults`, `TestAppConfigEachTimeoutFieldIndependentlyOverridable`, and `TestAppConfigFullyResolvedConfigPassesThroughUnchanged` cover `resolveConfig`'s three cases (partial override, every-field override, fully-pre-resolved pass-through). The scaffolder's own hermetic build/vet test (`TestGeneratedProjectBuildsAndVets`) covers the generated `main.go.in` template's converted `gwt.New(gwt.AppConfig{Config: cfg})` call.

Per Design Principle 7 (no speculative abstractions), no opt-out or escape hatch was added for `resolveConfig`'s "zero means default" behavior, and the functional-options mechanism should not be reintroduced without a fresh, explicit request — see `CLAUDE.md`'s "Things to avoid".

## API revision — 2026-08-02 (third pass: dead indirection + one more idiom)

A follow-up request to scan the whole codebase for similar clarity issues (after the first two passes) turned up one genuine dead-code finding and two smaller, explicitly user-approved touch-ups:

29. ✅ **`render.go`'s unexported "core" functions deleted; logic inlined into the methods.** `renderJSON`/`renderTemplate`/`renderServerError` existed so `Recover` could render an error response "without an `App` receiver" (per issue 23's original note) — but `Recover` is itself an `App` method (`func (a *App) Recover() Middleware`) and already called `a.RenderServerError`, never the unexported form. Grep confirmed nothing outside `render.go` called the three unexported functions, and inside `render.go` the only callers were the methods wrapping them. ## API revision — v3, 2026-08-03 (gin-style `Ctx` API)

The user tried the v2 API and asked for something "closer to gin gonic in style — intuitive, with sane defaults, maximum expressiveness for few lines." Four concrete verbosity drivers were measured in the v2 source before designing:

1. Handlers were bare `http.HandlerFunc` with no error return, so every failure path was a manual `app.RenderServerError(w, r, err); return` — 5 of the 8 lines in `examples/basic`'s POST handler.
2. Every render call took `(w, r, data, status)`, where `r` existed *only* to give the logger `r.Method`/`r.URL.Path`.
3. No request-side sugar: query params, JSON decoding, and headers were all raw `net/http`.
4. `RenderTemplate` took a path string and re-parsed from disk **on every request**.

Four decisions were put to the user before implementation; all four answers are recorded here because three of them touch standing prohibitions:

- **Handler signature:** `func(*Ctx) error` (echo/fiber-style) chosen over gin's literal `func(*Ctx)`, because the error return is what actually removes driver 1, and the stated goal was expressiveness rather than gin fidelity.
- **`Group`:** offered, and **declined** — routing stays flat. Item 26's prohibition stands, now reaffirmed rather than merely inherited. All ergonomic gain therefore had to come from `Ctx` itself.
- **Old `(w, r)` API:** clean break. The `Render*` helpers were deleted, not deprecated in place, matching item 23's precedent of removing the old form rather than keeping two ways to do one thing.
- **Uncommitted `examples/basic` expansion:** committed first as a v2 snapshot (`6a7945e`), then rewritten, so the v2 tour stays recoverable in history.

38. ✅ **`Ctx`, `Handler`, and `H` added (`ctx.go`).** `type Handler func(*Ctx) error`; `Ctx` carries exported `W`/`R` plus request helpers (`Param`, `Query`, `QueryDefault`, `FormValue`, `GetHeader`, `Bind`, `Context`, `Value`, `Identity`, `Logger`) and response helpers (`JSON`, `String`, `Stringf`, `HTML`, `NoContent`, `Redirect`, `SetHeader`, `Written`). All response helpers funnel through one unexported `write`, the single place `wroteHeader` is set. `H` is `map[string]any`.
    `String`/`Stringf` are split rather than one variadic `String`: `go vet`'s printf analysis infers a formatting wrapper and then flags every non-constant argument (`c.String(200, "hello "+user)`) — the `f` suffix is what makes vet check the format instead. It caught a real bug in gwt's own tests (`"100% done"` parsed as a `% d` verb) before the split.
    Done when: `ctx_test.go` covers every helper on both paths, including `TestCtxJSONMarshalErrorWritesNothingAndBecomes500` and `TestCtxHTMLExecuteErrorWritesNothingThen500` (buffering preserved — no partial bodies), `TestCtxBindMalformedBodyIs400NotA500`, and `TestCtxValueReadsForeignContextKeys`.

39. ✅ **Error contract added (`errors.go`).** `HTTPError{Code, Message, Err}` with `Unwrap`; `Status(code, message...)` and `StatusErr(code, err)`. `App.handleError` uses `AppConfig.ErrorHandler` if set, else `defaultErrorHandler`: `errors.As` finds an `*HTTPError` anywhere in the chain and uses its status/message; anything else renders a generic 500 with the real cause logged and **never** sent. 4xx logs at Warn, 5xx at Error, so a bad URL can't fill the error log at Error level.
    Includes the **committed-response guard**: because `return c.JSON(...)` is the documented idiom, a handler can respond in full and *then* return an error (a write failure inside `c.JSON`, a deferred cleanup). Writing a second status onto that response would corrupt it, so `handleError` checks `c.Written()` and only logs.
    The **panic path needed the same guard**, and initially shipped without it. `Recover` renders through the unexported `serverError`, not the `Ctx` error handler, so a handler that responded in full and then panicked produced `200 {"ok":true}{"error":"Internal Server Error"}` — `statusWriter` suppressed the duplicate `WriteHeader` but nothing suppressed the second `Write`. `serverError` now returns early when `w` is a `*statusWriter` with `wroteHeader` set; the always-on `Logging` middleware is what guarantees `w` is that type, since `Recover` runs inside it. Pre-existing in isolation (`http.Error` appended the same way), but v3 made "responded, then failed" the normal shape and left two error renderers disagreeing on the same condition.
    Done when: `TestPlainErrorBecomes500AndNeverLeaksTheCause` asserts the cause is in the log and absent from the body; `TestErrorAfterResponseCommittedDoesNotCorruptIt` and its panic-path twin `TestPanicAfterResponseCommittedDoesNotCorruptIt` assert the committed 200 payload survives with nothing appended; `TestHTTPErrorFoundAnywhereInTheChain`, `TestClientErrorsLogAtWarnAndServerErrorsAtError`, and `TestCustomErrorHandlerReplacesTheDefault` cover the rest.

40. ✅ **Middleware deliberately left as `func(http.Handler) http.Handler`.** The obvious move — making middleware `Ctx`-native for symmetry — was considered and **rejected on a correctness constraint**, not taste: CLAUDE.md documents that global middleware covers the mux's own 404/405 responses, and an unmatched request never reaches a route, so it has no `Ctx` and no wildcards. A `Ctx`-native global chain would have to synthesize a meaningless `Ctx` around the bare mux. Gin escapes this because its router owns `NoRoute`; stdlib `ServeMux` gives no such hook. Keeping the stdlib shape also preserves drop-in use of any third-party `http.Handler` middleware. The `Ctx` is therefore built in the route adapter inside `Handle` — the only place it is constructed.
    Done when: `TestHandlerCoversMuxNotFound` and `TestEndToEndDefaultAndUseMiddlewareOrder` pass unchanged in substance, proving 404 coverage and the fixed order survived the redesign.

41. ✅ **Routing rewritten to uppercase verbs (`router.go`).** `GET`/`POST`/`PUT`/`PATCH`/`DELETE` take a `Handler`; `Handle(method, pattern, h Handler, mw...)` keeps the generic form; new `HandleHTTP(method, pattern, h http.Handler, mw...)` is the raw `net/http` escape hatch that `ServeStatic` and `Handle` both build on. **No `HEAD` or `OPTIONS` method was added** — stdlib `ServeMux` already matches HEAD against a `GET` pattern, and `Handle`'s documented reason for existing is verbatim "for verbs without a dedicated method (e.g. `OPTIONS`)", so adding one would contradict the reason `Handle` survived `Group`'s deletion.
    Done when: `TestVerbHelpersRouteToCorrectHandlerAndPathValue`, `TestHandleAnyVerbWhenMethodEmpty`, and `TestHandleHTTPMountsPlainNetHTTPHandler` pass.

42. ✅ **Template set replaces per-request parsing (`render.go`).** `App.LoadTemplates(fsys fs.FS, patterns ...string) error` parses once (default pattern `"*.tmpl"`), taking an `fs.FS` so `os.DirFS` and `//go:embed` both work; `AppConfig.Templates` accepts a pre-built set. `Ctx.HTML(status, name, data)` executes by base filename. `RenderJSON`/`RenderTemplate`/`RenderServerError` were deleted.
    An unexported `serverError(w, r, err)` was **added back** for `Recover`, which is http-level and has no `Ctx`. CLAUDE.md warned against an unexported core layer here; that warning came from item 29, where the layer was proven **dead** — nothing called it. This one has exactly one real caller. The distinction that matters is "has a live caller," not "is unexported."
    Done when: `TestLoadTemplatesParsesMatchingFiles`, `TestLoadTemplatesExplicitPatterns`, `TestLoadTemplatesParseErrorIsReturned`, `TestLoadTemplatesNoMatchIsError`, `TestAppConfigTemplatesUsedWithoutLoadTemplates`, `TestCtxHTMLWithNoTemplatesLoadedIsCleanError` (no nil-deref on an unloaded set), and `TestServerErrorLogsAndWrites500WithoutLeakingTheCause` pass.

43. ✅ **`statusWriter` now forwards the optional `ResponseWriter` interfaces (`middleware.go`).** It embedded `http.ResponseWriter` and overrode only `WriteHeader`/`Write`, forwarding neither `http.Flusher`, `http.Hijacker`, nor `io.ReaderFrom`. Because `Logging` is always on and unremovable, anything it hid was unreachable in **every** gwt app — SSE, streaming, and WebSocket upgrades were all silently broken. Added `Flush`, `Hijack`, `ReadFrom`, and `Unwrap() http.ResponseWriter` (for `http.ResponseController`). `Hijack` over a non-hijackable writer returns `http.ErrNotSupported`, the same sentinel `ResponseController` uses, so a caller that type-asserts and then calls gets a correct answer rather than a panic.
    This is a **bug fix, not a feature**, and predates v3; it was fixed here because the redesign rewrites this exact path and `Ctx` adds another wrapper on top.
    Done when: `TestLoggingForwardsOptionalInterfaces`, `TestLoggingFlushReachesUnderlyingWriter`, and `TestLoggingHijackDelegatesAndReportsUnsupported` pass.

44. ✅ **Built handler cached; `Run` takes an optional address.** `Handler()` composed the global chain on **every** `ServeHTTP` call; it now builds once under a `sync.Once`. Known consequence, documented on `Use`: a `Use` call after serving has begun is silently ignored (previously it would have taken effect on the next request). `Run(addr ...string)` and `RunContext(ctx, addr ...string)` accept an optional address overriding `Config.Addr`, so `app.Run(":8080")` works gin-style.
    Done when: `TestUseWrapsWholeHandlerOnce` passes, and the server suite (`TestRunContextGracefulShutdownWaitsForInFlightRequest`, `TestRunContextRepeatedStartStop`) stays clean under `-race`.

45. ✅ **Example, scaffold, and docs rewritten.** `examples/basic` now embeds its templates via `//go:embed` and tours the `Ctx` helpers, the three error forms, and `HandleHTTP`; its `Example` smoke test grew to 14 assertions including exact error-body shapes. `cmd/gwt-cli/templates/main.go.in` was converted to the v3 API and now embeds `templates/`, which let the generated `Dockerfile` **stop copying `templates/`** into the runtime image (`static/` is still copied — `ServeStatic` reads it from disk). `doc.go`, `CLAUDE.md`, `ISSUES.md`, and `README.md` all rewritten.
    `README.md` was initially **missed** — it is the only doc nothing compiles or tests, so a full-repo API change can leave it silently stale (it had 28 v2-era references). Every Go snippet in it was then transcribed into a throwaway module and run through `go vet` against the real library, which is the only way to know they're right. Do that on any future API change; CLAUDE.md's "Repo layout" section now names all four doc files for this reason.
    Done when: `TestGeneratedProjectBuildsAndVets` (hermetic build+vet of the generated project) passes, the example was run as a real process with every route curled in both startup modes (normal and `CUSTOM_SERVER`), a scaffolded project was built and curled from both its own directory and another (proving embedded templates work cwd-independently while `ServeStatic` is cwd-relative), and every `README.md` snippet compiles and vets clean.

**Explicitly declined in this pass — do not add without a fresh, explicit request:**

- **`Group` / any prefix-scoped route builder.** Offered during the design questions and declined; routing stays flat.
- **`Ctx`-native middleware.** See item 40 — it breaks 404/405 coverage and stdlib interop.
- **Gin's `c.Set`/`c.Get`.** The `Ctx` is constructed in the innermost frame, after all middleware, so nothing downstream of the handler could read what `c.Set` wrote — it would be a local variable with extra steps. And a gwt-namespaced key can't read what foreign middleware wrote under its own key type, so the interop argument fails too. Gin's version works only because gin middleware is `func(*gin.Context)` in the same chain, which item 40 deliberately rejected. `Ctx.Value(key any) any` is the read side that *does* have a consumer. Adding `Set`/`Get` would repeat item 29 exactly: an abstraction justified by a premise that was false from the start.
- **`:id` path syntax.** Patterns stay stdlib `{id}`. A translation layer would be the "magic path transformation" this repo rejects, and it would break `{path...}` wildcards. `Ctx.Param` reads them.
- **A `Ctx.SetStatus` method.** It would be indistinguishable from `NoContent(status)`.

## API revision — v3.1, 2026-08-03 (one error shape everywhere)

v3 shipped with an inconsistency flagged at the time but left for the user to decide: handler errors rendered as JSON, while `Auth`'s 401 and the mux's own 404/405 were stdlib's plain text. A client written against "gwt returns JSON errors" choked on both. The user asked for it fixed.

46. ✅ **Every gwt-generated error response is now JSON.** A shared unexported `writeJSONError(w, status, message)` in `errors.go` writes `{"error":"<message>"}` for the three paths that have no `Ctx` to render through — `Recover`'s 500 (`serverError`), `Auth`'s 401, and the mux's 404/405. `defaultErrorHandler` produces the identical shape via `Ctx.JSON`. Since those two writers are reached by different code, only an end-to-end assertion holds them together: `TestEveryErrorPathRendersTheSameShape` exercises all five situations (handler error, panic, `Auth` rejection, no route, wrong method) and asserts status, exact body, and `Content-Type`.
    Done when: that test passes, plus `TestMethodNotAllowedKeepsStdlibAllowHeader` — rewriting a 405's body must not cost the `Allow` header, which is its only machine-readable part.

47. ✅ **The mux's own 404/405 intercepted by elimination, not by a route lookup.** `muxErrorsAsJSON` wraps the mux (innermost global wrapper, so `Logging` still reports the true status and `Recover` still covers it) in a `notFoundWriter` that rewrites the body of any 4xx/5xx written through it. What makes that safe is `HandleHTTP`'s registered wrapper **stepping out of** `notFoundWriter` before running the handler: every registered route therefore bypasses it, so anything still writing through it is necessarily the mux answering for itself.
    **The obvious implementation was tried first and rejected on measurement.** Asking `ServeMux.Handler(r)` which pattern matches reads far more directly — an empty pattern means "no route" — but benchmarking showed it costs ~200ns/48B/2allocs, *as much as the entire `mux.ServeHTTP` call it precedes*, on every request, to benefit only the ones that 404. Measured end-to-end on a 5-route app: 1638 ns/op, 229 B/op, 10 allocs/op with the lookup versus 1429/181/8 without. The by-elimination version costs one wrapper allocation and no measurable time (1443 ns/op, 229 B/op, 9 allocs/op).
    Two traps found while building it, both now guarded by tests:
    - `ServeMux.Handler(r)` **cannot be used to serve**, only to predicate — the handler it returns does not populate path wildcards, so `Ctx.Param` silently returns `""` (`TestPathValuesSurviveTheNotFoundWrapper`).
    - Stdlib answers trailing-slash and path-cleaning requests with a **301**, not a match. Treating those as "no route" would turn every such redirect into a 404. `notFoundWriter` passes statuses below 400 through untouched (`TestRedirectsAreNotRewrittenAsNotFound`).
    A third alternative — registering a catch-all `"/"` route to own the not-found response, which would be free — was tested and rejected: it swallows the 405, returning 404 with no `Allow` header for a method mismatch on a more specific pattern.
    Done when: the tests above pass, and stepping out keeps a route's writer the fully-featured `statusWriter`, so `notFoundWriter` never sits in a streaming path and needs only `Unwrap`.

48. ↩️ **`HandleHTTP` and `ServeStatic` deliberately left alone.** A raw `net/http` handler mounted with `HandleHTTP` owns its response, error format included — that is the entire point of the escape hatch. `ServeStatic` is built on it, so a missing asset still returns `http.FileServer`'s plain-text 404. Beyond consistency, intercepting it would mean wrapping the writer `http.FileServer` uses for its `sendfile`/`ReadFrom` fast path, slowing every file served to change the format of responses no browser reads.
    Done when: `TestHandleHTTPErrorsAreLeftAlone` pins the behavior so a later "consistency" pass doesn't quietly change it.

## API revision — v3.4, 2026-08-04 (`CORS`, `CSRF`)

The user asked what security middleware gwt was missing relative to best practice. Two gaps stood out: CORS (previously Deferred as "not requested") and CSRF (previously Deferred pending "its own dedicated design pass," bundled with session storage/issuance). 61. ✅ **`App.CORS(cfg CORSConfig) Middleware` shipped in `security.go`.** `CORSConfig` is a plain struct (`AllowedOrigins`, `AllowedMethods`, `AllowedHeaders`, `ExposedHeaders`, `AllowCredentials`, `MaxAge`) — no functional options, consistent with Principle 3. Reopens the prior "not requested" Deferred entry; the entry's reasoning was never architectural, only that nobody had asked. Implementation notes: a genuine CORS preflight (`OPTIONS` carrying `Access-Control-Request-Method`) is detected and answered by `CORS` itself — `204`, `next` never called — since an unmatched-method `OPTIONS` would otherwise reach the mux and get its own 405 rewritten to JSON; a non-preflight bare `OPTIONS` is untouched and still reaches a registered `app.OPTIONS(...)` route (`TestCORSNonPreflightOptionsReachesRegisteredHandler` guards the composition). A disallowed-origin **actual** request is never rejected server-side — CORS is browser-enforced, so the handler still runs and returns its normal status, just without `Access-Control-*` headers (`TestCORSActualRequestDisallowedOriginPassesThroughWithoutHeaders`); rejecting it would break same-origin and non-browser (curl, service-to-service) callers that happen to send an `Origin` header. `Vary: Origin` is added on every origin-dependent response and omitted only for the pure-wildcard/no-credentials case, where the response doesn't depend on origin at all. `App.CORS` panics at setup (see item 63) if `AllowCredentials` is combined with a wildcard `AllowedOrigins` entry, since CORS itself forbids that combination.

62. ✅ **`App.CSRF(cfg CSRFConfig) Middleware` shipped in a new `csrf.go`, using the stateless double-submit cookie pattern.** Chosen specifically because gwt has no server-side session store (still deferred, see below) — double-submit needs none: a signed cookie is issued on a safe request (GET/HEAD/OPTIONS) and must be echoed back, via the `X-CSRF-Token` header or (only when `Content-Type` is a form type, so a JSON body is never drained by `r.FormValue` ahead of `Ctx.Bind`) a `csrf_token` form field, on an unsafe one. Token = a 32-byte `crypto/rand` nonce plus its HMAC-SHA256 signature (keyed by `CSRFConfig.Secret`), both base64url-encoded; cookie-vs-submitted comparison uses `subtle.ConstantTimeCompare`. Cookie is `HttpOnly` (the server hands the token to templates directly via `Ctx.CSRFToken`, so client JS never needs to read the cookie), `SameSite=Lax`, `Secure` per `CSRFConfig.Secure` (caller-gated, e.g. on `Env == "prod"` — same convention as `HSTS`, not auto-derived). An already-valid token is never rotated — only issued/refreshed when absent or invalid — since rotating on every response would invalidate a token already embedded in an in-flight page render. Exposes the token to handler code via the exact same trio pattern `auth.go` established: unexported `csrfContextKey`, package-level `CSRFToken(r *http.Request) (string, bool)`, and `Ctx.CSRFToken() (string, bool)` delegating to it.
    **A real interaction surfaced wiring this into `examples/basic`:** that file also demonstrates a plain JSON API (`POST /items`), and wiring `CSRF` globally via `Use` 403'd every one of those calls, since a bearer/API-key-style JSON endpoint has no CSRF cookie to check. Fixed by wiring `CSRF` **route-level** in `examples/basic` (mirroring how `Authentication` is already demonstrated there), protecting only the new `/csrf-demo` routes — `POST /items` is untouched. The scaffold wires it **globally** instead, since its only unsafe-method route (`POST /page`) is exactly the form CSRF is meant to protect and there's no conflicting JSON route. Also documented: `SameSite=Lax` means the CSRF cookie never reaches a cross-site subrequest, so a credentialed cross-origin write (`CORSConfig.AllowCredentials`) fails at the cookie-never-arrives stage rather than the token stage — this CSRF middleware targets same-site form/AJAX flows by design, not credentialed cross-origin APIs. And if a `CORSConfig.AllowedHeaders` is set explicitly alongside `CSRF`, it must list `X-CSRF-Token` or a cross-origin CSRF-protected write fails as a CORS rejection instead of a CSRF 403.
    Done when: `go build ./...`, `go vet ./...`, `go test ./...`, and `go test -race ./...` are clean; `csrf_test.go` covers token issuance/non-rotation, header- and form-field-based acceptance, the JSON-body-untouched case, missing/invalid/mismatched-token rejection, the empty-secret panic, the token-validation helper directly (genuine/tampered-nonce/tampered-signature/wrong-secret), and `CSRFToken`/`Ctx.CSRFToken` parity with and without the middleware in the chain; `TestEveryErrorPathRendersTheSameShape` gained a CSRF-403 case.

Three items surfaced by studying two sibling projects (`go-pkm`, `go-heartbeat`) that migrated onto loom by hand rather than via `loom new`. Neither sibling project is modified by this work — they are read-only reference signal.

68. ✅ **Documented the `"/"` subtree-match footgun (no API change).** stdlib `http.ServeMux` treats a pattern of exactly `"/"` as a subtree match — it catches every request that isn't matched by anything more specific, not just an exact root request; `"/{$}"` is exact-root-only. `Handle`/`GET`'s doc comments (`router.go`), README's Routing section, and CLAUDE.md's `router.go` bullet all now call this out. `TestHandleBareSlashIsSubtreeMatchNotExactRoot` (`router_test.go`) pins that loom does no pattern rewriting of its own and that an unmatched path under `"/{$}"` still reaches loom's own JSON 404. Signal: `go-heartbeat` hit this as a real production bug — a dashboard route registered at bare `"/"` silently absorbed unrelated unmatched paths — and had to add its own regression test around it.
    Done when: `Handle`/`GET`'s doc comments, README's Routing section, and CLAUDE.md's `router.go` bullet all mention it, and `TestHandleBareSlashIsSubtreeMatchNotExactRoot` passes.
69. ✅ **Promoted `loadDotEnv` from the scaffold template into the library as `loom.LoadDotEnv(path string) error` (`config.go`).** Both `go-pkm` and `go-heartbeat` — which migrated onto loom by hand rather than via `loom new` — independently hand-rolled near-identical copies of the scaffold's function; promoting it removes the duplication for any future hand-migration and lets the scaffold itself call the real thing. The promoted signature matches the richer contract both sibling apps converged on independently, not the scaffold's original weaker one: `os.IsNotExist` alone is silently ignored, any other `Open`/`Setenv`/scan error is returned, and matching-quote stripping is included. `cmd/loom/templates/main.go.in` now calls `loom.LoadDotEnv(".env")` instead of embedding its own copy.
    Done when: `config_test.go`'s new `TestLoadDotEnv*` tests pass, `go build/vet/test(-race) ./...` are clean, `cmd/loom`'s `TestGeneratedProjectBuildsAndVets`/`TestGeneratedProjectActuallyRuns` are clean, and no `loadDotEnv` (lowercase, scaffold-local) identifier remains in `cmd/loom/templates/`.
70. ✅ **Added `App.AuthenticationRedirect(cfg AuthenticationRedirectConfig) Middleware`, a new sibling to the unchanged `Authentication`.** A config-struct replacement of `Authentication` itself was considered — matching `CORSConfig`/`CSRFConfig`'s shape (Principle 3) and this repo's own precedent (items 23, 56) of replacing rather than duplicating a canonical entry point — but the user explicitly chose the additive sibling constructor instead, to keep zero call-site churn and two single-purpose entry points (one JSON-401-only, one redirect-only) rather than one dual-mode struct with an empty-string-means-something-different field. `AuthenticationRedirectConfig{Authenticate, LoginPath}`: `Authenticate` has the same contract as `Authentication`'s; `LoginPath` is required and must be a local path starting with a single `/` (not `//`) — `AuthenticationRedirect` panics at setup otherwise (an off-site value would be a fixed open redirect on every route it protects, the same panic-at-setup category as `CORS`'s wildcard+credentials check). On failure it responds `303 See Other` to `LoginPath` — chosen over a configurable status code (Principle 8: no field for an unconfirmed need), since both sibling apps use 303. This is a **deliberate, documented third exception** to "every loom-generated error response is JSON" (CLAUDE.md's Conventions section and doc.go both updated) — redirect mode has no JSON body by design. Signal: both `go-pkm` and `go-heartbeat` bypass `Authentication` entirely and hand-roll their own redirect-based middleware, citing exactly this limitation (`go-heartbeat`'s `auth.go` comment: "NOT loom's built-in Authentication primitive, which only supports a JSON 401 response with no allowlist/redirect concept"). **This change deliberately does not add any exemption-list/allowlist mechanism** (both sibling apps' own per-request allowlist-checking) — that edges toward the already-declined `Group`-style grouping/prefix mechanism (Design Principle 8) and needs its own fresh, explicit request; noted here as a follow-up someone could raise later, not designed now. The credential/cookie/session mechanism itself remains entirely out of loom's scope, unchanged — `Authenticate` is still the caller's closure; loom still issues, signs, and stores nothing.
    Done when: `go build/vet/test(-race) ./...` are clean, `TestAuthenticationRedirectSendsSeeOtherOnFailure`/`TestAuthenticationRedirectAcceptsAndSetsIdentity`/`TestAuthenticationRedirectPanicsOnNilAuthenticateOrUnsafeLoginPath` pass, and every README snippet touched was verified via a throwaway `replace`-module build+vet.

**Explicitly declined in this pass — do not add without a fresh, explicit request:** a global-plus-allowlist exemption mechanism for authentication middleware (checked per-request against an exact-path/prefix list, as both sibling apps hand-rolled) — this edges toward the already-declined `Group`-style prefix/grouping mechanism (Design Principle 8) and needs its own explicit request and design pass, not a rider on this one.

## Deferred (explicitly out of scope — not oversights)

- **Form parsing/validation.** Reason: not part of v1 either; genuinely new scope with no prior art to restore, deserving its own design pass.
- **Session storage/issuance.** Reason: this is the security-sensitive surface the original "Sessions, cookie auth, CSRF" deferral was hedging on — it still deserves its own dedicated design pass rather than being bolted on. Narrower than the original deferral, and narrower still after v3.4: Tier 6 shipped a generic `Authentication` middleware primitive (route-level, scheme-agnostic — the caller supplies the actual credential check) plus `SecureHeaders`/`HSTS`, and v3.4 shipped stateless CSRF (`App.CSRF`, double-submit cookie — see the v3.4 section above) specifically *because* it needs no session store. `Authentication` remains a building block someone could use to implement session-based auth on top of; gwt itself still doesn't issue, sign, or store sessions.
- **`RequestID` middleware, `App.Routes()` route introspection, `AppConfig.BaseContext` beyond the minimal passthrough already specified.** Reason: speculative — no confirmed use case yet. Per Design Principle 7 ("no speculative abstractions"), these land only when something real needs them. (Note: `AppConfig.BaseContext` itself — the minimal passthrough to `http.Server.BaseContext` — is implemented in `app.go`/`server.go`, since it's part of the documented API surface; only *extensions* beyond it are deferred.)
- **Registry push / CI-CD for scaffolded Docker images.** Reason: go-pkm's `update_image` script (the reference pattern) is purely local build-and-restart with no registry step; v2's scaffold matches that scope deliberately and does not add CI/CD.
